route 53 Routing policies
-simple - typically route traffic to a single resource. can specify multiple values in the same record, client chooses randomly. when alias enabled, specify only one aws resource. cant be associated with health checks

-weighted - control the % of the requests that go to each specific resource, assign each record a relative weight. dont need to sum 100. dns records must have the same name and type, can be associated with healt checks. load balancing between regions, testing new application versions.  

-failover - set health check (mandotary) in case of primary being unhealthy the secondary (disaster recovery) will take over and the client will get its result. 

-latency based - least latency close to us, super helpful when latency for users is a priority, can be combined with health checks

-geolocation - based on user location. specify location by continent, country or by us state. can be associated with health checks 

-multi-value - when routing traffic to multiple resources, route 53 return multiple values, resources. can be associated with health checks. up to 8 healthy records are return for each multi-value query. not a subsutite for ELB. 

-geoproximity (using route 53 traffic flow feature) - based on the geographic location of users and resources, ability to shift more traffic to resources based on the defined bias. to change the size of the geographic region, specify bias values. resources: AWS or non aws resources - must use route 53 traffic flow (advanced) - helpful to shift trafic using bias

-ip based : based on client's ip addresses. you provide a list of CIDRs for your clients and the corresponding endpoints/locations. optimizes performance, reduce network costs. route end users from a particular isp to a specific endpoint.

S3 - Obj Encryption 
----Server-Side Encryption (SSE)
-sse-s3: using keys handled, managed and owned my aws. obj is encrypted server side. encryption type is aes-256. enabled by default for new buckets and new objects. must set header "x-amz-server-side-encryption": "AES256"

-sse-KMS: keys handled and managed by AWS KMS (key management service). user control + audit key usage using cloudtrail. must set header "x-amz-server-side-encryption": "aws:kms" / Limitation: you may be impacted by the kms limits. when you upload, it calls the GenerateDataKey KMS API. when you download, it calls the Decrypt KMS API. Count towards the kms quota per second. you can request a quota increase using the Service Quotas Console

-sse-c: fully managed by the customer outside of AWS. amazon s3 does not store the encryption key you provide. https must be used. encryption key must be provided in http header, for every http request made.

S3 Object Lock (versioning must be enabled)
WORM 
block an object version deletion for a specified amout of time 

-Retention mode - Compliance:
similar to glacier vault lock. object versions cant be overwritten or deleted by any user, including root. object retention modes cant be changed, and retention periods cant be shortened

-Retention mode - Governance:
most users cant overwirte or delete an obj version or alter its lock settings. some users have special permissions to change the retention or delete the object. 

-Retention period: protect the obj for a fixed period, it can be extended. 

-legal hold: protect the obj indefinitely, independent from retention period. can be freely placed and removed using the s3:PutObjectLegalHold IAM permission

CloudFront vs S3 Cross Region Replication
CloudFront:
- Global Edge network
- Files are cached for a TTL (maybe a day)
- Great for static content that must be available everywhere

S3 Cross Region Replication:
- Must be setup for each region you want replication to happens
- Files are updated in near real-time
- Read only
- Great for dynamic content that needs to be avaliable at low-latency in few regions

AWS Global Accelerator

the Anycast ip send traffic directly to edge locations
the edge locations send the traffic to your application

- consistent performance
- health checks
- security 


AWS Global Accelerator vs CloudFront
- they both use the aws global network and its edge locations
- both integrate with AWS shield for ddos protection

cloudfront:
improves perf for both cacheable content (images, videos)
dynamic content - api acceleration and dynamic site delivery

global accelerator:
improves perf for a wide range of applications over tcp or udp
proxying packets at the edge to applications running in one or more aws regions

good for http use cases that required deterministic, fast regional failover

-unlimited throughput, unlimited number of messages in q 
-default 4 days, maximus 14 days 
-low latency
-can have duplicate messages
-messages up to 1024 kb 
-consumers poll up to 10 messages 
-consumers delete messages after processing them 
-encryption: in flight, at rest using kms, client side

Long polling: when a consumer requests messages from the q, it can optinally wait for messages to arrive if there are none in the q. API: WaitTimeSeconds

Amazon Kinesis Data Streams
collect and store streaming data in real-time (Click streams-iot devices-metrics&logs) -> producers (apps-kinesis agent) -> amazon kinesis data streams -> Consumers (app-lambda-amazon data firehose-managed service for apache flink)

-retention between up to one year
-ability to reprocess (replay) data by consumers
-data cant be deleted from kinesis until it expires 
-data up to 1mb 
-data ordering guarantee for data with the same "Partition ID"
-at rest kms-encryption. in flight https encryption
-kinesis producer library (KPL) to write an optimized producer app 
-kinesis client library (KCL) to write an optimized consumer app

capacity modes:
-provisioned mode: choose number of shards - each shard gets 1mb/s in, 2mb/s out. scale manually to increase or decreas the number of shards. you pay per shard provisioned per hour 
-on demand mode: no need to provision or manage the capacity. default capacity provisioned. scale auto. pay per stream per hour and data in/out per GB. 



Amazon Data Firehose 
send data from sources to target destinations. you can do data transformations using lambda before sending

fully managed service
automatic scaling, serverless, pay for what you use.
NEAR REAL TIME with buffering capabilitybased on size / time


Kinesis Data Streams vs Amazon Data Firehose

Kinesis Data Streams:
Streaming data collection.
Producer and consumer code required.
Real-time processing.
Provisioned or On-Demand capacity modes.
Stores data for up to 365 days.
Supports replay capability.

Amazon Data Firehose:
Loads streaming data into S3, Redshift, OpenSearch, third-party destinations, or custom HTTP endpoints.
Fully managed service.
Processes data in near real-time.
Automatically scales.
Does not store data.
Does not support replay capability.


SQS vs SNS vs Kinesis 

SQS:
Consumer “pulls data”.
Data is deleted after being consumed.
Allows unlimited workers (consumers).
No need to provision throughput.
Ordering is guaranteed only for FIFO queues.
Supports individual message delay.

SNS:
Pushes data to many subscribers.
Supports up to 12,500,000 subscribers.
Data is not persisted (lost if not delivered).
Follows the Pub/Sub model.
Supports up to 100,000 topics.
No need to provision throughput.
Integrates with SQS for fan-out patterns.
Provides FIFO capability for SQS FIFO.

Kinesis: 
Standard mode uses pull data (2 MB per shard).
Enhanced fan-out uses push data (2 MB per shard per consumer).
Supports replaying data.
Designed for real-time big data, analytics, and ETL.
Provides ordering at the shard level.
Data expires after X days.
Supports provisioned mode and on-demand capacity mode.
